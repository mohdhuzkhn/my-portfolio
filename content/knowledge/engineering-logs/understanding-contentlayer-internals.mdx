Contentlayer connects authored content to application code. It reads content files, validates their metadata against document schemas, and generates typed objects that pages can import.

## The problem it solves

Without a content pipeline, an application must implement and maintain several steps itself:

```text
Read files
Parse Markdown and MDX
Parse frontmatter
Validate document metadata
Generate application types
Report content errors
```

Centralizing these steps gives content authors a consistent structure and lets application code work with documents instead of repeatedly parsing raw files.

## How Contentlayer works

### 1. Scan content directories

The configuration defines the content root and the file patterns associated with each document type. This platform organizes its source files by domain:

```text
content/
  knowledge/
  projects/
  research/
```

The Knowledge document type matches `knowledge/**/*.mdx`, including articles nested inside subdirectories.

### 2. Validate document schemas

Each document type declares its fields, required values, and defaults. In this platform, Knowledge articles require a title, summary, and category. Publication status controls whether an article appears in the public collection.

```yaml
title: Understanding Contentlayer Internals
summary: How MDX becomes typed application content.
category: AI Engineering
status: PUBLISHED
tags:
  - Contentlayer
  - MDX
```

Schema validation exposes missing or invalid metadata during content generation. Build output should be checked for errors and warnings so invalid documents are not silently overlooked.

### 3. Generate typed content objects

Contentlayer generates collections from the document type names. This repository uses:

```typescript
import {
  allKnowledgeArticles,
  allProjects,
  allResearchPapers,
} from "contentlayer/generated";

const publishedArticles = allKnowledgeArticles.filter(
  (article) => article.status === "PUBLISHED",
);
```

The application's content helpers use these collections to build cards, category navigation, article pages, and related-content links. Computed fields add values such as URLs, slugs, and estimated reading time.

### 4. Render the compiled MDX

Document metadata drives the page header, while the compiled MDX body renders the article. Markdown headings, lists, links, and correctly closed code fences determine the structure; the site's typography styles determine how that structure looks.

Contentlayer does not repair malformed Markdown automatically. An incorrectly closed code fence can cause the following prose to render as code, so content needs a visual review as well as schema validation.

## Benefits

- **Type safety:** generated types make content fields easier to use correctly in application code.
- **Consistency:** shared schemas establish the same metadata requirements across documents.
- **Performance:** content is processed ahead of page rendering rather than parsed from source on every request.
- **Developer experience:** pages consume structured objects and compiled content through a common interface.

## The role of the database

Content generation and database synchronization are separate stages. Contentlayer produces file-based application data. A separate synchronization script can persist that content and its relationships in PostgreSQL for database-backed features.

This separation keeps MDX as the authoring source while allowing the platform to build navigation and static pages from generated collections.

## Design lessons

Treat document schemas as an interface between authors and application code. Define required fields deliberately, keep document names consistent with generated imports, and validate both metadata and rendered content before publishing.
