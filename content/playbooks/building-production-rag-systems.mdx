overview: "Most RAG tutorials stop at 'retrieve and generate.' Production RAG is mostly the parts that come after that: evaluation, guardrails, and handling the documents that don't fit your assumptions."
problem: "A RAG demo that works on ten clean PDFs usually breaks on a real document corpus — inconsistent formatting, duplicate content, and documents that contradict each other."
prerequisites: "A working embeddings + vector store setup; familiarity with the tradeoffs in the Chunking Strategies knowledge article."
recommendedStack: "A vector store with metadata filtering (Qdrant or pgvector), a reranker, and a generation model with a context window large enough to hold reranked results comfortably."
commonMistakes: "Treating retrieval and generation quality as one metric — a system can generate fluent, well-cited answers from the wrong retrieved chunk, and that failure is invisible unless retrieval is evaluated separately."
tradeoffs: "Reranking adds latency for a precision gain; skipping it only makes sense once you've measured that your base retrieval precision is already high enough for your domain."
steps: [
  { "order": 1, "title": "Establish a retrieval-only evaluation set", "detail": "Before touching generation quality, build a set of queries with known-correct source chunks, so retrieval precision can be measured independently of how fluent the final answer sounds." },
  { "order": 2, "title": "Pick a chunking strategy deliberately", "detail": "Match the strategy to your corpus's actual structure — see the Chunking Strategies knowledge article for the concrete tradeoff." },
  { "order": 3, "title": "Add reranking once retrieval precision plateaus", "detail": "Rerankers help most when the vector store's raw top-k is noisy; measure before adding the latency cost." },
  { "order": 4, "title": "Add a citation check before shipping", "detail": "Verify generated citations actually correspond to retrieved chunks — this is what catches silent retrieval failure, per the Enterprise RAG Architecture page." },
  { "order": 5, "title": "Re-run the retrieval eval after every corpus change", "detail": "Document corpus changes are the most common cause of retrieval regressions that generation-level evals won't catch." }
]

Building a RAG demo and building a RAG system that survives production traffic are different jobs. This playbook is the second one — the execution path, not the concept explanation (that's what the Knowledge base entries are for).
